# OpenWiki 修复任务书（2026-07-12，风险复核修订版）

> 本文档用于指导 AI 编码代理分批修复 OpenWiki。原始体检发现的问题大多成立，但第一版方案把数据迁移、主列表重构、隐私开关和大规模删代码放在同一分支，且 B1/B2/B3 存在方案级风险。本修订版以当前 `origin/main` commit `1206c3f` 为基线，已经按实际代码重新核对。

## 0. 已确定的技术与产品决策

以下决定已经确认，执行者不得自行改成其他方案：

1. **不做一个包含全部任务的大 PR。** 按本文的“执行车道”分别开分支和 PR，每个 PR 可独立回滚。
2. **B1 不直接增加后台自动重试。** 先保证失败后仍可手动重试并留下可见状态；自动重试要等编译过程具备幂等或事务保护后另行设计。
3. **B2 拆分图谱关系类型。** TF-IDF 相似关系使用 `similar`，Q&A 引用关系使用 `qa_reference`；不再共用 `related`。
4. **B3 分两阶段。** 先阻止产生新孤儿文件，稳定后再迁移历史孤儿；历史文件只隔离，不物理删除。
5. **B4/B5/B6 作为同一个主列表数据流 PR。** 不与其他功能修复或死代码清理混做。
6. **C15 是独立隐私功能 PR。** Jina 抓取和 Google 翻译分别提供开关，默认开启以保持现有行为，并明确说明数据外发。
7. **D3 删除无入口的 data-hub 页面。** 只删页面和页面专属代码，搜索、Markdown 导出等仍在使用的能力必须保留。
8. **D 批次最后单独清理。** 不把几千行删代码与行为修复混在同一个 PR。

## 3. 高风险任务

### B1. Wiki 编译失败后保持可重试和可诊断

**位置**：`src-tauri/src/ai/wiki_engine.rs` 的 `auto_compile` 失败分支与 `wiki_compile_log`。

**已确认问题**：失败分支错误地更新 `wiki_assessed_hash`，后续入口守卫把内容当作已处理。当前代码没有周期性扫描失败内容的调度器；`compile_content` 还会在多次 AI 调用之间逐步写页，直接增加后台重试可能放大部分成功后的重复写入。

**本轮改法**：

1. 删除失败分支的 `update_content_assessed_hash`，成功/明确跳过时才更新 hash。
2. 保留 `wiki_compile_log.status = error` 和完整错误信息。
3. 把“失败收尾”提取为可单测的小函数，验证释放锁、记录错误且不更新 assessed hash。
4. 确认内容卡片现有手动编译入口在失败后仍能重新获取锁并执行；若错误完全不可见，只增加最小的失败状态/重试提示，不增加后台队列。
5. 不加入 `HashMap` 退避、不加定时器、不在启动时批量重跑旧内容。

**验收**：

- 模拟失败后 assessed hash 保持原值或 `NULL`；
- compile lock 状态变为 error，不残留 compiling 锁；
- 同一内容随后手动编译可以重新获取锁；
- 不产生后台重复 API 请求；
- 记录后续“事务化/幂等编译后再做自动重试”的 follow-up，不在本 PR 扩大范围。

### B2. 拆分并迁移图谱关系类型

**位置**：`src-tauri/src/lib.rs` 启动清理、`src-tauri/src/ai/wiki_engine.rs::link_pages_by_shared_tags`、`src-tauri/src/commands/wiki.rs::save_chat_message_as_page`、repository 的 wiki edge 方法。

**已确认问题**：TF-IDF 相似边和 Q&A 引用边都使用 `related`。启动时删除全部 `related` 会删掉 Q&A 引用；只改成“一次性删除”又会让之后已经失效的相似边永久残留。

**本轮改法**：

1. 新保存的 TF-IDF 边统一使用 `similar`。
2. 新保存的 Q&A 引用边统一使用 `qa_reference`，保持现有双向语义。
3. 增加一个事务化、幂等的关系迁移函数，并用 app setting 记录完成状态；标志只能在事务成功提交后写入。
4. 迁移时先识别涉及 `page_type = 'qa'` 的旧 `related` 边，以 `INSERT OR IGNORE` 写成 `qa_reference` 后删除对应旧边，避免部分迁移后的唯一键冲突；再删除剩余旧 `related` 边。
5. 对已经丢失的 Q&A 边，通过 `wiki_pages.source_message_id -> wiki_chat_messages.pages_used` 重建；解析必须兼容字符串 ID 和 `{id,title}` 形式。
6. 每次 TF-IDF 重建前只删除 `similar`，然后重新计算；绝不删除 `qa_reference`。
7. 不创建新的表或改变用户知识页正文；只改变 edge relation 值和可推导的边。

**验收**：

- 迁移连续运行两次，第二次数据库不再变化；
- 保存 Q&A 页后重启两次，`qa_reference` 边仍存在；
- 修改普通页面 tags 后重建，过期 `similar` 边消失，新边正确出现；
- 没有 tags 的 Q&A 页不会参与 TF-IDF，但引用边仍显示；
- 构造已经丢边但保留 `pages_used` 的数据，迁移可恢复引用；
- 在用户数据库副本上先验证边数量和 Q&A 引用，再允许合并。

### B3a. 阻止产生新的剪贴板图片孤儿

**位置**：`capture/clipboard.rs`、`capture/detector.rs`、`commands/capture.rs::save_content_auto`、`BubbleView.tsx`。

**已确认问题**：剪贴板图片先写入 captures；保存时在查重前又复制并生成缩略图。取消、去重拦截、替换 pending、自动保存、保存失败等路径都可能留下文件。

**本轮改法**：

1. 剪贴板临时图片写入 `captures/.pending/`，路径创建逻辑集中到一个 Rust helper，不再在多个文件硬编码应用数据目录。
2. 图片字节 hash 必须在生成正式副本和缩略图之前计算并查重。
3. 只有 `.pending/` 中由 OpenWiki 创建的文件允许 move；用户导入、Spotlight 或截图目录中的源文件只能 copy，绝不能移动原文件。
4. 同卷 pending 文件成功保存时 move 到正式路径；随后生成缩略图并写数据库。若缩略图或数据库写入失败，清理本次产生的正式文件/缩略图，并保留或恢复 pending 文件供用户重试。
5. 重复内容只更新时间，不生成正式副本或缩略图；pending 文件在成功动画不再需要预览后清理。
6. 取消、倒计时、失败自动关闭、dedup 抑制、pending 被新捕获替换、bubble 关闭和自动保存路径都必须明确清理所属临时文件。
7. 清理 helper 必须校验 canonical path 位于 `.pending/`，拒绝删除任意外部路径。

**验收矩阵**：

- 复制图片后取消：无 pending 常驻、无正式文件、无缩略图；
- 等待超时：结果同上；
- 保存成功：数据库 1 条、正式图 1 张、缩略图至多 1 张、pending 为 0；
- 保存重复图片：不新增正式图和缩略图，pending 最终为 0；
- 保存时报数据库错误：原图仍可重试，不出现半条数据库记录；
- pending 显示期间复制第二张图：被替换或被忽略的文件都有明确归属和清理；
- 导入本地图片：原始用户文件仍在原位置且字节不变；
- confirm 和 auto-save 两种 capture mode 都通过。

### B3b. 历史孤儿图片隔离

**前置条件**：B3a 已合并并完成一次用户实测。不得与 B3a 同 PR。

**本轮改法**：

1. 先实现 dry-run，只输出候选清单，不移动文件。
2. 引用集合必须包含数据库所有记录（包括 `is_deleted = 1`）的 `image_path` 和 `thumbnail_path`，并统一 canonicalize 后比较。
3. 排除 `.pending/`、已有 `_orphaned/`、数据库文件、日志及非图片文件。
4. dry-run 清单经人工抽查后，才允许移动到 `captures/_orphaned/<timestamp>/` 和 `thumbnails/_orphaned/<timestamp>/`。
5. 同目录写 `manifest.json`，记录原路径、隔离路径、大小和时间；不得物理删除。
6. 操作重复运行不得重复移动或覆盖同名文件。

**验收**：使用生产数据库和文件目录的副本执行；候选清单与数据库引用路径的交集必须为 0；隔离后应用历史图片全部可打开；按 manifest 可完整恢复。

### B4-B6. 服务端筛选、稳定回焦与搜索定位

**位置**：`ContentList.tsx`、`contentStore.ts`、`storageService.ts`、`commands/storage.rs`、`storage/repository.rs`、`App.tsx` 搜索跳转。

**范围**：一个 PR，按 B4、B5、B6 三个 commit 实施。当前 UI 只有类型、导入文档和日期筛选，本轮不新增“分类”筛选。

#### B4 服务端筛选与计数

1. 后端查询接受 `content_type/document/date_range/hide_sensitive/limit/offset`；导入文档判定必须与当前 `source_app in ('Markdown 导入','导入内容')` 语义一致。
2. Rust 已有 `contains_sensitive_data`。把同一检测函数注册为 SQLite deterministic scalar function，`hide_sensitive=true` 时在 `WHERE` 中先过滤再分页；查询结果、总数和各 tab 计数必须使用同一规则。不得在 LIMIT/OFFSET 后再过滤，也不得删除敏感过滤能力。
3. 查询和 count 共用同一套条件构造，全部参数化；排序至少使用 `captured_at DESC, id DESC` 保证稳定。
4. 筛选变化时取消或忽略旧请求结果，重置分页并请求第一页，避免慢请求覆盖新筛选。
5. `hasMore` 根据当前筛选 count 计算，不再使用全库 total。
6. 若结果不足一屏但 `hasMore=true`，主动继续加载，不能只依赖滚动事件。
7. 后端补查询、count、敏感过滤、文档类型和日期边界单测。

#### B5 回焦刷新不缩页、不跳位置

1. 回焦使用独立的后台 refresh，不设置会卸载列表的全屏 `isLoading`。
2. 保留当前已加载数量和筛选条件；不得每次固定退回 50 条。
3. 刷新前记录顶部可见 content id 和像素偏移，刷新后恢复视觉锚点；只保存 `scrollTop` 不足以应对顶部新增内容。
4. 限制单次回焦请求大小；若用户已加载极多内容，优先刷新顶部窗口并合并，不在每次 focus 拉取数千条。

#### B6 搜索结果定位

1. 点击内容搜索结果时，把类型和日期筛选都恢复为 all；敏感过滤保持用户设置，搜索结果本身也必须遵守敏感过滤。
2. 后端提供在稳定排序下定位目标位置/所在页的查询；不采用“把单条旧内容硬插到顶部”的方案。
3. 加载目标所在连续页后再滚动和高亮；无论成功、被敏感过滤还是目标已删除，都清空 `scrollToId`。
4. 失败时显示轻量提示，不让 effect 在后续列表更新中重复重置筛选。

**统一验收**：

- 用临时数据库写入至少 300 条混合内容，覆盖同时间戳、敏感文本、导入文档和四种日期范围；
- 各 tab 数字从首屏开始正确且不随滚动变化；
- 每个筛选能加载全部结果，不重复、不漏项；
- 加载 150 条后切走再回来，数量和视觉位置保持，新内容出现在正确位置；
- 搜索第 250 位内容后能定位、高亮并清空跳转状态；
- 敏感过滤开启时，列表、计数和搜索都不暴露敏感项；
- v0.3.21 批量 URL 导入、文件导入、删除、高亮、URL 更新事件全部回归通过。

### B7. 图谱停止后台无效绘制

**改法**：优先把 `active` 从 App 传到 WikiView/WikiGraphView，并使用 d3 simulation 的 tick/end 驱动绘制；tab 不可见或 simulation 结束时停止，拖拽、缩放、主题/数据变化时按需重绘。除非 active 传递不足，不优先引入 IntersectionObserver。

**验收**：布局稳定后绘制计数停止；切到其他主 tab 后停止；拖拽/缩放恢复流畅；切换主题立即重绘正确颜色。

## 4. 局部修复任务

### C1. 更新下载失败可见且可重试

复用现有 `failed` 状态。后台下载失败时显示错误；主按钮执行真正的重新下载，发布页作为独立 fallback，不把“打开发布页”伪装成“重试”。断网失败、恢复网络重试、安装失败三个路径分别实测。

### C2. URL 重试结束后恢复按钮且不覆盖成功原文

后端失败事件继续带 `failed=true`；若原 `raw_text` 已是成功正文则不覆盖，只报告错误。ContentCard 只在重试期间监听与自己 id 匹配的完成事件，成功或失败都清理 listener 和 loading；另加超时兜底。不得为 50 张卡片常驻增加 50 个 listener。

### C3. 老内容重试/OCR 使用按 ID 查询

`retry_url_fetch` 和 `ocr_image` 改用现有 `get_content_by_id`，补第 500 条之后内容的 repository/command 测试。

### C4. OAuth HTTP 请求加超时

`oauth.rs` 两处、`gemini_oauth.rs` 四处统一使用 30 秒 client timeout；授权回调 listener 的 180 秒等待保持不变。验证 OAuth 授权页可打开。

### C5. PKCE/CSRF 使用系统随机源

使用已经存在的 `rand 0.8` 和 `OsRng`，删除 xorshift。测试输出长度、字符集以及连续调用不相同；测试不宣称能证明随机强度。

### C6. Wiki lint 去重且重启保留

按 `lint_type + page_ids + status=open` upsert；重复扫描更新时间和文案，不新增记录。移除启动时无条件 resolve orphan。扫描结束时只 resolve 本轮已经不再成立的问题。补连续三次扫描、问题消失、重启保留测试。

### C7. OpenWiki 自写剪贴板抑制

建立一个统一的 Rust 写剪贴板命令：写入前登记 text hash 和短过期时间，watcher 命中后只跳过一次。所有活跃的前端 `navigator.clipboard.writeText` 和 Rust `set_text` 调用都改走该入口；删除前的死模块不要求迁移。验证复制正文、错误报告、导出路径、MCP 摘要均不触发捕获，外部应用复制相同文本仍可在窗口期后正常捕获。

### C8. Windows 跟随系统语言

使用 `sys-locale` 获取 Windows 系统语言，不让执行者改成手写 Windows API。macOS 现有 `defaults` 优先级不变；把 locale 归一化提成纯函数，测试 `en-US/zh-CN/zh-Hans` 等输入。PR 标明 Windows 仅代码级验证，正式合并前要求 Windows 构建通过。

### C9. Spotlight 精确去重

依赖 B3a 的统一 hash 计算。Spotlight 在调用保存前保留本次 hash；duplicate 时调用 `find_content_by_hash(hash)`，不得再取最新一条，也不得解析错误字符串猜 ID。测试同时插入另一条更新内容时，备注仍落在 hash 匹配记录上。

### C10. 中英文文案一致

补齐 content loading key；radarStore 返回稳定错误码/枚举，组件负责翻译；topic tag 比较使用稳定原始值而不是翻译后的字符串。中英文分别验证加载、解析失败和 legacy radar。

### C11. Radar listener 清理竞态

采用 `const promise = listen(...); return () => promise.then(unlisten => unlisten())` 模式。开发 StrictMode 下事件只触发一次加载。

### C12. 合并两处 N+1 IPC

在 L6 后执行。内容列表新增批量 `content_ids -> wiki pages` 命令并由列表层分发；ContentCard 手动编译成功后只刷新本卡映射。WikiPageDetail 一次调用 `get_contents_by_ids(ids)` 后按 id 回填。实测 50 张卡片只产生 1 次批量 IPC，详情来源只产生 1 次 IPC。

### C13. 无效动画类

删除无效 Tailwind plugin 类，使用项目已有 framer-motion 实现 150-200ms 的 opacity/轻微位移动画，遵守 DESIGN.md 的 minimal-functional 规则，不新增依赖。

### C14. 深色主题响应

使用现有 CSS 变量或 dark class；图谱主题必须来自响应式状态而不是 render 时直接读取 DOM。浅色/深色切换不需要重新进入页面。

### C15. URL 第三方服务透明化与开关

独立功能 PR：

1. 新增 `use_jina_reader` 和 `translate_foreign_content` 两个设置，默认 `true` 保持现状。
2. 关闭 Jina 时通用路径从 direct HTML 开始，失败再走 headless WebView；平台专用 reader 保留原有顺序。
3. 关闭翻译时不调用 Google Translate，保留原文。
4. 设置页和中英文 README 明确说明：Jina 会收到完整 URL，Google Translate 会收到待翻译文本；部分平台 reader 仍会访问对应平台/API，不能宣传成“完全离线”。
5. 设置读取失败时沿用当前默认开启，不因异常悄悄改变用户抓取行为。

验收矩阵：两个开关四种组合分别抓取普通英文网页；通过日志/代理确认请求域名；关闭 Jina 后仍能读取可直连网页；关闭翻译后正文不出现自动中文翻译。

### C16. 杂项

- 删除 BubbleView 三处生产 `debug_log`；
- WikiLintSection 使用函数式 setState；
- 两项同 commit，但不得混入其他清理。

## 6. 最终验收与发布边界

每个 PR 只验收自己的行为；所有 PR 合并后再做一次集成回归：

1. `cargo check`、`cargo test --lib`、`npm run build`、`npm run lint` 全绿；
2. Windows release job 能编译；
3. 捕获：文本、URL、图片、取消、默认保存、去重、Spotlight；
4. 内容：分页、筛选、日期、敏感过滤、搜索定位、回焦、删除、文件/URL 批量导入；
5. Wiki：自动编译失败、手动重试、Q&A 保存、重启、图谱重建、lint；
6. 洞察：Radar 加载、生成、导出、事件监听；
7. 设置：中英文、深浅主题、URL 隐私开关、导出路径；
8. 死代码清理后四个主页面、BubbleView、Spotlight 和 Markdown 导出无回归。

本任务书不负责发版。全部 PR 验收完成、用户确认后，再按 `release-notes/README.md` 单独执行发版流程。
